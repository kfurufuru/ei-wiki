# 生成AIの動向と現場への含意

**対象読者**: :material-account-hard-hat: 電気担当 / :material-account: 計装担当

---

## 30秒まとめ

生成AIは「質問に答える道具」から、**指示を受けて自分で手順を組み立てて動く「エージェント」**へ重心が移っています。プラント保全でも、過去の故障記録と図面を読ませて原因と対策を返す仕組みが実運用に入りました。

一方で、社内文書に答えさせる仕組み（RAG）の失敗の大半は**AIではなく文書側**（不足・古い・ばらばら）で起きています。日本では2025年9月にAI推進法が全面施行され、2026年3月改定のAI事業者ガイドラインは「人間が最終判断できる仕組み」を利用者にも求めています。

現場でやるべきことは変わりません。**手順書と記録を整えること、AIに任せない判断の線を引くこと**の2つです。

!!! warning "このページは腐りやすい"
    動向・数値・事例は2026年9月時点のものです。製品名・モデル名は書きません（[生成AIの基本](basics.md) と同じ方針）。判断に使うときは末尾の「根拠」に挙げた出典を直接確認してください。

## 何が変わったか：「答えるAI」から「動くAI」へ

これまでの生成AIは、人が1回質問して1回答える往復でした。今は、**目標を渡すと、必要な情報を自分で探し、複数の手順を順に実行して結果を返す**使い方が主流になりつつあります。これを **AIエージェント（AI Agent）** と呼びます。

| | 答えるAI（チャット） | 動くAI（エージェント） |
|---|---|---|
| 人がすること | 毎回、質問と材料を渡す | 目標と参照先と禁止事項を最初に決める |
| AIがすること | 1回答える | 検索→判断→実行→確認をくり返す |
| 失敗の出方 | 答えが間違う | **間違ったまま先へ進む** |
| 現場での例 | 「この症状の原因候補を挙げて」 | 「過去記録と図面を見て原因と対策を提示し、報告書の下書きまで作って」 |

総務省・経済産業省の AI事業者ガイドライン（第1.2版、2026年3月31日公表）は、AIエージェントを「特定の目標を達成するために、環境を感知し自律的に行動するAIシステム」と定義しました（二次資料経由。原文は「根拠」参照）。

!!! danger "失敗の出方が変わる"
    チャットの間違いは人が読んで気づけます。エージェントの間違いは**次の手順の入力になって連鎖**します。自律性を上げるほど、**どこで人が止めるか**を先に決めておく必要があります。設備の起動・停止・設定変更をAIの判断で実行させないという線は、[注意事項・情報セキュリティ](security.md) の「最終判断はエンジニア」を踏襲します。

M365 Copilot で自分の業務にエージェントを作る手順は [Copilotエージェントの作り方](copilot-agents.md) を参照してください。

## 現場で効く3つの型

### 型1：社内文書に答えさせる（RAG）

**RAG（Retrieval-Augmented Generation、検索拡張生成）** は、AIが答える前に社内の文書を検索し、見つけた文書を根拠にして回答する仕組みです。取扱説明書・過去の仕様書・保全記録を「AIに読ませる」用途の大半はこれです。

RAGの効果は**AIの性能より文書の状態で決まります**。ある企業の社内ヘルプデスクでの試験運用では、評価228件のうち「良い」は約3分の1にとどまり、悪かった原因の内訳は次のとおりでした。

| 悪かった原因 | 割合 |
|---|---|
| 文書の不備・不足（必要な情報がそもそも書かれていない） | 46 % |
| 検索精度（正しい文書を引けない） | 42 % |
| 生成AI自体の精度 | 12 % |

出典: キヤノンITソリューションズ テクニカルレポート（「根拠」参照）。

つまり、**9割近くは文書側の問題**です。取扱説明書が古い版のまま、保全記録が担当者のメモに散っている、設定値がどこにも書かれていない、という状態でAIを入れても答えられません。

!!! tip "現場でのRAGの前提条件"
    - **記録が残っている**こと。[故障モード棚卸し](../05-hozen/failure-mode-inventory.md) の「行の割り方」と「設定情報の復元性」の考え方がそのままRAGの前処理になります
    - **版が管理されている**こと。古い規程を引用して答える事故は、権限管理だけでは防げません
    - **閲覧権限が文書に付いている**こと。RAGは「その人が読める文書だけから答える」設計にしないと、権限を越えた情報が漏れます

### 型2：手順を任せる（エージェント）

毎月同じ指示を書いて同じ型の報告書を作っているなら、それはエージェント化の候補です。作り方・権限・費用の考え方は [Copilotエージェントの作り方](copilot-agents.md) が正典です。ここでは動向として1点だけ補足します。

エージェントが社内システムやツールを呼ぶための共通規格として **MCP（Model Context Protocol）** が広く採用されています。2024年11月に公開され、2025年12月に業界団体へ移管された公開規格で、主要なAIツールの多くが対応しています。「AI側とツール側を同じ口金でつなぐ規格」と理解すれば十分です。

現場で意識すべきは規格そのものではなく、**つないだ先に何をさせるか**です。

- **基本は読み取り専用**にする。書き込み（データ更新・メール送信・設定変更）は人の承認を挟む
- **出所を確認**する。公式提供のものか第三者製かで信頼度が違う。2025年には悪意あるサーバーに接続すると利用者のPCで任意のコマンドが実行される脆弱性が報告されています
- **操作履歴を残す**。AIが何を呼んで何をしたかを追える記録が無いと、事故の原因が追えません

### 型3：設備データ×AI（故障診断・予知保全）

プラント・工場の保全で、公開されている実用事例です。

| 事例 | 発表 | 何をするか | 効果（発表値） |
|---|---|---|---|
| 空調機器メーカーと電機メーカーの協創：設備故障診断エージェント | 2025年4月 | 保全技術者が発見したポンプ・バルブ等の故障を入力すると、**原因と対策を提示**。設備図面をナレッジグラフ化し、保全記録と故障原因分析プロセスを学習 | 回答10秒以内、精度90 %以上。2025年9月までに試験運用完了し国内外拠点へ展開予定 |
| 電機メーカー：品質保証AIエージェント（製造業向けに提供） | 2026年4月提供開始 | 過去のトラブル対応記録・マニュアル・仕様書から、**事例検索と対応レポート作成**を自動化。熟練者の知見100件以上を組み込み | 社内先行導入で事例検索時間約9割減、レポート作成・原因分析時間8割以上減 |

!!! note "生成AIと「自律制御AI」は別物"
    石油化学プラントでのAIによる常時自動運転（2023年〜）や強化学習による制御の正式採用（2023年）も「プラントのAI」として並んで報道されますが、これらは**機械学習・強化学習による制御**であり、文章を生成するAIではありません。本ページの主題（文書・記録・判断支援）とは技術も導入の重さも違います。混同して「うちも生成AIで自動運転」と語らないでください。

上の2事例に共通するのは、**AIが読んでいるのは過去の記録と図面**という点です。記録が無ければ学習させるものがありません。型1と同じ結論に戻ります。

## ルールの動き：AI推進法とAI事業者ガイドライン

### AI推進法（2025年施行）

日本で初めてAIを正面から扱う法律が2025年5月に成立し、同年9月1日に全面施行されました。特徴は次のとおりです。

- **推進型の法律**で、直接の罰則はない（二次資料による。「根拠」参照）
- 事業者には、AIの研究開発・活用にあたり**安全性の確保に努める努力義務**がある
- 2025年12月に「AI基本計画」が閣議決定され、補助・税制・規制サンドボックスが2026年以降に段階実施される

現場の電気計装担当が直接何かを届け出る法律ではありません。ただし、**会社としてAIツールの一覧化・利用ガイドライン・運用記録**が求められる方向で、それは現場の「何を入力してよいか」に直結します（[注意事項・情報セキュリティ](security.md) が正典）。

### AI事業者ガイドライン 第1.2版（2026年3月）

法的拘束力のない指針（ソフトロー）ですが、取引先・顧客からの信頼の基準として機能しています。第1.2版の主な改定点は次の3つです。

1. **AIエージェント・フィジカルAI（物理環境で自律的に動くAI）を定義に追加**
2. 自律性の高いAIについて、「判断が必要となる事項を重要度に応じて整理し、**人間の判断を適切に介在させる仕組み**の構築が重要」と明記
3. AI推進法・政府向けガイドラインへの参照を追加

**AIを使う側（AI利用者）** に期待される事項として挙げられているのは、次の4点です。

- 提供者から案内されたルールの順守
- 異常時の迅速な情報共有
- 定期的な操作履歴の確認と報告
- **自動化バイアス対策**：AIの判断を過度に信頼せず、自らの確認を継続する

「自動化バイアス」は、機械が出した答えを人が疑わなくなる傾向のことです。保護継電器の整定値や絶縁判定をAIに聞いて、出てきた数値をそのまま使うのがまさにこれです。本Wikiが接地・絶縁などの数値の正典ページを1つに決めている理由と同じ問題意識です。

## 今日からできる5つ

| # | やること | なぜ |
|---|---|---|
| 1 | チームで使っているAIツールを一覧にする | 法・ガイドラインの第一歩。何を使っているか分からないと規程が作れない |
| 2 | 「AIに任せない判断」を明文化する | 設備の起動・停止・整定変更・作業許可はAIの出力を根拠にしない。[注意事項・情報セキュリティ](security.md) の検証義務を具体化 |
| 3 | 保全記録の書き方を揃える | RAG・故障診断エージェントはどちらも記録を読む。[故障モード棚卸し](../05-hozen/failure-mode-inventory.md) の行の割り方に合わせる |
| 4 | 取扱説明書・仕様書の**版**を管理する | 古い文書を引用して答える事故はAI側では防げない |
| 5 | AIに出させた数値は正典ページで検算する | 自動化バイアス対策。[生成AIの基本](basics.md) のハルシネーション対策と同じ |

### 原本未照合（honest-hold）

- **AI事業者ガイドライン第1.2版の原文PDFは、作成時に取得できませんでした**（サーバーが応答を拒否）。「AIエージェント」の定義文とAI利用者への期待4点は PwC の解説記事からの引用です。**原文と食い違う場合は原文が正**です
- **AI推進法の条文は e-Gov で逐語照合していません。** そのため本ページは**条番号を書いていません**。「罰則なし」「努力義務」は二次資料の記述です。社内規程に落とす際は必ず e-Gov の条文で確認してください（feedback-rules R5）
- 事例の効果数値（10秒・90 %・9割減）は**各社の発表値**であり、本Wikiが検証したものではありません。自社に当てはめる根拠には使えません

### 意図的に書かなかったもの

- **モデル名・製品世代・料金**。数か月で変わるため（R10）
- **市場調査の導入率・成長率**。出典により定義がばらつき、現場の判断に効かないため
- **事例の企業名を本文では業種で表記**しました。出典表には正式なリンクを載せています

### 限界の明示

- 本ページはツール・ベンダーの推奨ではありません。**業務で使えるツールは会社の契約と情報セキュリティ規程で決まります**
